# 0.6.3 Gateway Capabilities

The 0.6.3 release branch turns more of the local Mixle capability surface into
audited HTTP endpoints. The gateway remains the serving and orchestration
package: core probability, uncertainty, model fitting, and substrate logic stay
in `mixle`, while `mixle-mlops` owns request authentication, persistence,
queues, route registration, spend gates, and deployment boundaries.

This guide covers the release-branch additions in `mixle-mlops`.

## Scope

0.6.3 adds or expands these gateway surfaces:

- Substrate serving for knowledge shards, retrieval, context assembly,
  factuality receipts, publishing, and promotion approval.
- Telemetry ingestion for PII-free decision events and training rows.
- Pool job submission with budget, confirmation, quota, spend, and artifact
  round-trip checks.
- Creation verbs for certified model artifacts, UQ, simulation, verified
  synthesis, skill registration, and lineage.
- Mixle model serving manifests with certificate and calibration metadata.
- Drift retraining that promotes only after a drift-triggered refit.

All paths below are mounted by `mixle_mlops.gateway.app.create_app()` under
`/v1`, except `/health` and the existing auth/MCP surfaces.

## Substrate Serving Contract

Substrate endpoints expose the retrieval half of the reasoning loop. The
gateway retrieves evidence, assembles budgeted context, and returns an abstain
decision when evidence is too weak. It does not generate an answer inside the
`/context` route. The caller must either answer using the returned context and
citations or respect `abstain: true`.

Substrate shards persist under:

```text
{registry_root}/substrate/{name}
```

The persisted format is the same shape written by core `mixle.substrate`, so a
local daemon and the shared gateway can exchange shards without a migration.

Example context request:

```json
{
  "query": "Which model produced the latest porosity estimate?",
  "budget": {"max_chars": 2500, "max_items": 12, "shape": "passages"},
  "hops": 2,
  "min_confidence": 0.25,
  "compress": true,
  "scope": "team"
}
```

Factuality checks are different: the route receives an answer that already
exists, extracts/checks claims against the substrate, and returns a claim-level
receipt with citations and unsupported claims.

## Governance And Sharing

Publishing and promotion are explicit. A normal user can publish items to a
scope when allowed by the request guard and can propose items for promotion.
Curated promotion requires admin approval through the approval endpoint. This
keeps cross-team knowledge movement auditable rather than making visibility a
side effect of retrieval or ingest.

## Telemetry Contract

Telemetry events are decision records, not raw content. A pushed event should
carry:

```json
{
  "kind": "route",
  "features": {"confidence": 0.82, "model": "local-student"},
  "choice": "answer-local",
  "outcome": {"accepted": true, "latency_ms": 18},
  "tags": {"surface": "cascade"}
}
```

Events persist per authenticated user under:

```text
{registry_root}/telemetry/{user}/events.jsonl
```

`GET /v1/telemetry/training/{kind}` returns the rows used to train learned
orchestration policies. Static policies remain the teacher until a learned
policy is receipted as no worse on this history.

## Pool Jobs And Spend Rails

Pool endpoints expose a small job gateway over the core `mixle.pool`
discipline. Rails run before work:

- `est_cost > budget` rejects the job.
- A priced job requires `confirm: true`.
- A job that would exceed quota rejects before execution.
- Rejected jobs cost nothing.
- Completed fit jobs return a serialized artifact and canonical parameter
  fingerprint so clients can reload and check bit-exact round trips.

The 0.6.3 server-side executor supports `spec.op == "fit"`:

```json
{
  "kind": "fit",
  "reason": "nightly local refit",
  "est_cost": 0.0,
  "spec": {
    "op": "fit",
    "data": [0.1, 0.0, 0.2, 0.15],
    "seed": 0,
    "max_its": 25
  }
}
```

Unknown operations are recorded as rejected outcomes rather than surfaced as
untracked failures.

## Creation Verbs And Lineage

The `/create`, `/uq`, `/simulate`, `/synthesize`, `/skills`, and `/lineage`
routes are HTTP twins of core Mixle creation and artifact operations.

`POST /v1/create` stores a model with:

- certificate guarantee,
- calibration verdict when requested,
- strategy,
- row count,
- data fingerprint,
- parameter fingerprint.

`POST /v1/synthesize` accepts a declarative verifier instead of an arbitrary
Python callable. The current verifier shape supports field index checks with
`min`, `max`, or `in` constraints, and echoes that constraint in the response so
clients can re-check rows independently.

`GET /v1/lineage/{model_id}` connects the exact training data fingerprint to
the stored model and every skill exposing it.

## Mixle Model Manifests

`MixleAdapter.info()` now enriches model metadata with certificate and
calibration manifests when the hosted model can provide them. This allows a
client to gate on how a model was estimated and whether uncertainty was
checked, not only on the model id.

Advertised capabilities are still capability-gated:

- `predict` requires CDF support or sampling.
- `score` requires log-density support.
- `latent` requires latent-structured support or a Viterbi path.
- `decide` requires sampling.
- `chat` always exists as a concise summary surface.

## Drift Retraining

The drift retrain entrypoint compares a recent batch against the production
reference. If drift is detected, it refits, registers, promotes a new
production version, and rolls the reference forward. If no drift is detected,
the production alias is untouched.

This path is intentionally conservative: no silent refit happens without a
drift receipt, and the tests assert both the promotion and no-op cases.

## Validation Map

Release tests cover the following behaviors:

- `tests/test_substrate_serving.py`: ingest, retrieval, context abstention,
  multi-hop provenance, persistence, factuality, publish/propose/approve/reject.
- `tests/test_telemetry_serving.py`: push, stats, training rows, unknown-kind
  rejection, persistence, per-user scoping.
- `tests/test_pool_serving.py`: budget rejection, confirm rail, quota, artifact
  round trip, spend accounting, queue listing.
- `tests/test_verbs_serving.py`: create, calibration, UQ, honest UQ
  degradation, simulation, synthesis, skills, lineage.
- `tests/test_drift_retrain.py`: drift-triggered promotion and no-drift no-op.

## Boundaries

- The gateway persists artifacts and queues locally under `registry_root`;
  production deployments should put that root on durable storage.
- `/context` returns evidence and an abstain decision; it does not generate the
  answer.
- `/synthesize` accepts declarative constraints, not arbitrary Python
  functions over HTTP.
- Pool job execution is deliberately narrow in this slice. New operation kinds
  should be added as explicit, tested executors with budget and spend rails.
